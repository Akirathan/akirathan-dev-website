## Early days

Many years ago, I started with GitHub Copilot.
Since I was recognized as an open source contributor, I got Copilot for free, so why not use it.
At that time, it was pretty much inline code completion that generated nonsense 80% of the time.
But the rest of the time, it was still quite useful, especially for unit tests with rather repetitive code.

My friend introduced me to [Claude Code](???) a few months after it was released.
My first reaction was shock, just like for many other people.
I was genuinely impressed that the AI can now scan the entire code base and just write code instead of me.

## My setup nowadays

Pretty soon, I ran into organization problems - having too many tabs open in my terminal was just too chaotic for me.
While looking for tools that could help me with that, I came across [Orca](???), an [ADE](???) (Agentic Development Environment) that lets you orchestrate dozens of subagents across dozens of worktrees while still keeping a good overview of what is going on.

I don't have any other subscription except for Claude.
I don't see any need for it - Claude gets the job done for me pretty well.
I experimented with hosting an open-weight `qwen` model on a spare PC that is just sitting in a bedroom.
Its results were so poor that I dropped the experiment immediately.
Apparently, 6 GB of VRAM is just too little.

## What do I use it for?

<Subtitle>Even better question: "What **don't** I use it for?"</Subtitle>

Nowadays, I use Claude Code for pretty much everything: accounting, analytics reporting, marketing, code, and 3D model generation and modification.
Obviously, writing code seems to be its strongest trait.

## To review or not to review?

I approach reviewing code from Claude just like I approached reviewing code from my colleagues:
- Understand the motivation and the gist of the change.
- Always review the tests first, then identify the important parts.
  - For example, the color of a button in an internal tool is super unimportant, while fiddling with client-sensitive data is important.
- Don't go into too much detail, unless I am genuinely interested in it.
- If the code is generally readable, approve it. If not, try to steer the agent towards cleaner code and modify the instructions.

The only difference is that the back-and-forth is much quicker.

I try to delegate more and more work to AI agents, but I still have trust issues.
I guess this is common across the entire industry.
I usually don't let them just run wild and publish any changes without at least a quick review.

## Missing the old days?

Some devs say they miss coding.
I don't, at least not much.
Writing code was never the biggest part of the job.
I would estimate that I spent at most 20% of the time writing code; the rest I spent **reading code** - either doing reviews or reading some library code.
From time to time, I satisfy my hunger for writing code by rewriting some generated code that I don't like myself, rather than re-prompting the agent.

## My limitations

To me, an AI agent is just a magical black box that spits out some output based on the context.
I don't understand the details - too much statistical theory for my taste - and I don't want or need to understand them now, just like I don't need to understand the details of many other technologies that I use.

Like many other organizations, I don't have experience with using AI agents at scale, in a team of multiple people.
I am eager to learn more interesting patterns of how to use them.
